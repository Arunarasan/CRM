# Arudra CRM — REST API Documentation

Generated by reading the controller, DTO, entity, security, and exception-handling source directly (Java 17 / Spring Boot 3.2.5). No code was modified to produce this document.

## 1. Overview

**Base URL:** `/api` (no `server.servlet.context-path` is configured, so paths below are relative to the application host/port, e.g. `http://localhost:8080/api/...`)

**Auth scheme:** JWT Bearer token. Send `Authorization: Bearer <token>` on every request except the `/api/auth/**` endpoints.

From `SecurityConfig.java`:
```java
.authorizeHttpRequests(auth -> auth
        .requestMatchers("/api/auth/**").permitAll()
        .anyRequest().authenticated()
)
```
- `/api/auth/**` — public (`permitAll()`), no token required.
- Every other `/api/**` path — requires a valid, non-expired JWT (`anyRequest().authenticated()`), enforced by `JwtAuthenticationFilter` running before `UsernamePasswordAuthenticationFilter`. Session policy is `STATELESS`.
- `@EnableMethodSecurity` is on, but only **`CustomerController`** actually uses `@PreAuthorize` (role/authority checks). Every other controller has **no method-level role restriction** — any authenticated user (any role) can call any endpoint on the other 16 controllers, including HR, payroll, purchasing, deletes, etc. This looks like a gap rather than an intentional design, and is worth flagging to reviewers.
- Unauthenticated requests to a protected path return **401** with the plain-text body `"Unauthorized - Invalid or Expired Token"` (set directly on the response by the custom `authenticationEntryPoint`, not via `ApiError`/`ApiResponse`).
- CORS: `@CrossOrigin(origins = "*")` is declared on every controller *and* a separate `CorsConfigurationSource` bean restricts allowed origins to `app.cors.allowed-origins` (default `http://localhost:5173`) with credentials allowed — the two configurations are redundant/inconsistent (the controller-level `@CrossOrigin("*")` is normally overridden by the global CORS bean, but this is worth a second look).

### Standard success envelope — `ApiResponse<T>` (`dto/ApiResponse.java`)

```json
{
  "success": true,
  "message": "Success",
  "data": { /* T */ },
  "timestamp": "2026-07-17T10:00:00"
}
```

**Important finding:** although the task brief assumes all responses use this envelope, **only `CustomerController` and `DashboardController` actually wrap their responses in `ApiResponse<T>`.** Every other controller (`AuthController`, `BillingController`, `ContractorController`, `ExpenseController`, `HrController`, `InventoryController`, `LeadController`, `MeasurementController`, `NotificationController`, `ProjectController`, `PurchaseController`, `QuotationController`, `ReportController`, `SiteVisitController`, `TaskController`) returns the raw entity/DTO/`Page`/`List`/`Map` directly as `ResponseEntity<T>`, with no `success`/`message`/`timestamp` wrapper. `AuthController` returns yet another ad-hoc shape — raw `Map.of("success", ..., "message", ...)` on error paths, or `AuthResponse`/`TokenRefreshResponse` POJOs directly on success. This inconsistency is called out again inline under each controller's "Response" column.

### Standard error shape — `ApiError` (`exception/ApiError.java`), produced by `GlobalExceptionHandler`

```json
{
  "timestamp": "2026-07-17T10:00:00",
  "status": 404,
  "error": "Not Found",
  "message": "...",
  "path": "/api/customers/999",
  "requestId": "generated-uuid"
}
```

`GlobalExceptionHandler` (`@ControllerAdvice`) maps:

| Exception | HTTP Status | Notes |
|---|---|---|
| `ResourceNotFoundException` | 404 Not Found | message = exception message |
| `MethodArgumentNotValidException` (`@Valid` failures) | 400 Bad Request | `message` = concatenated `field: defaultMessage` list |
| `AccessDeniedException` (`@PreAuthorize` failure) | 403 Forbidden | generic message, does not leak details |
| `AuthenticationException` | 401 Unauthorized | generic message |
| `SQLIntegrityConstraintViolationException` | 409 Conflict | e.g. duplicate entry |
| `Exception` (catch-all) | 500 Internal Server Error | stack trace is logged server-side but **not** returned to the client |

**Note:** `AuthController` does *not* rely on this handler for its own known failure cases — it catches `BadCredentialsException`/`LockedException`/generic `Exception` itself inside `/login` and returns plain `Map` bodies with its own status codes (401, 423 LOCKED, 500), bypassing the `ApiError` shape entirely. The `authenticationEntryPoint` for an expired/missing JWT also bypasses `ApiError` (plain text body via `response.sendError`). `@Valid` is not actually used anywhere in the 17 controllers examined (no `MethodArgumentNotValidException` is realistically triggered by current code), so the 400 case is effectively dead code today.

### Pagination convention

Most list endpoints accept `@RequestParam(defaultValue="0") int page` and `@RequestParam(defaultValue="10") int size` (or `20` for notifications) and return a Spring Data `Page<T>` (fields: `content`, `totalElements`, `totalPages`, `number`, `size`, etc.) — either raw or, for Customer/Dashboard, inside `ApiResponse.data`.

## 2. AuthController — `/api/auth` (public, `permitAll()`)

| Endpoint | Description |
|---|---|
| `POST /api/auth/login` | Authenticate with email/password, returns JWT + refresh token |
| `POST /api/auth/refresh` | Exchange a refresh token for a new access token |
| `POST /api/auth/forgot-password` | Request a password-reset token (mocked email) |
| `POST /api/auth/reset-password` | Consume a reset token and set a new password |

### `POST /api/auth/login`
- **Auth:** none (public)
- **Body** (`AuthRequest`): `{ email: string, password: string, rememberMe: boolean }`
- **Response 200** (`AuthResponse`, raw — **not** `ApiResponse`): `{ token, refreshToken, email, name, roles: string[] }`
- **Behavior:** Uses Spring `AuthenticationManager`; on success resets `failedAttempts`, creates a refresh token (`RefreshTokenService.createRefreshToken(userId, rememberMe)`), and logs the attempt to `LoginHistory` (with `ipAddress` from `request.getRemoteAddr()`).
- **Failure paths (handled locally, not via `GlobalExceptionHandler`):**
  - Bad credentials → `401` with `{success:false, message:"Invalid email or password"}`, and increments `failedAttempts`; after 5 failed attempts the account is locked (`accountNonLocked=false`, `lockTime` set) and a `LoginHistory` row with status `FAILED` is written.
  - Locked account → `423 LOCKED` with `{success:false, message:"Account is locked..."}`.
  - Any other exception → `500` with `{success:false, message: <exception message>}` (leaks raw exception text to the client — notable since `GlobalExceptionHandler`'s generic handler deliberately hides this).

### `POST /api/auth/refresh`
- **Auth:** none
- **Body** (`TokenRefreshRequest`): `{ refreshToken: string }`
- **Response 200** (`TokenRefreshResponse`, raw): `{ accessToken, refreshToken }` (echoes back the same refresh token string)
- **Response 401**: `{success:false, message:"Refresh token is invalid or expired!"}` if not found/expired.

### `POST /api/auth/forgot-password`
- **Auth:** none
- **Body** (`ForgotPasswordRequest`): `{ email: string }`
- **Response 200**: `{success:true, message:"If the email exists, a password reset link has been sent."}` — always returns success regardless of whether the email exists, to prevent user enumeration.
- **MOCKED:** Email sending is not implemented. The controller does `System.out.println("MOCK EMAIL SENDER: Password reset link: http://localhost:5173/reset-password?token=" + token)` instead of sending a real email.

### `POST /api/auth/reset-password`
- **Auth:** none
- **Body** (`PasswordResetRequest`): `{ token: string, newPassword: string }`
- **Response 200**: `{success:true, message:"Password reset successfully."}` if token valid, unexpired, and purpose `PASSWORD_RESET`.
- **Response 400**: `{success:false, message:"Invalid or expired token."}` otherwise.

- **Body:** `CustomerDTO` (see fields above)

### `POST /api/customers/{id}/activities`
- **Body:** `CustomerActivityDTO`: `{ action, description }`

- **Body:** `CustomerNoteDTO`: `{ noteType, content }`

## 11. MeasurementController — `/api/measurements`

**Auth mechanism is different from every other controller:** the create/update/room-add endpoints require two custom request headers, `X-User-Name` and `X-User-Role`, instead of reading the identity out of the JWT/`SecurityContext` like the rest of the app does. This is inconsistent with the JWT-Bearer scheme documented for the rest of the API and should be flagged — a caller must still hold a valid JWT (global filter still applies), but the "who performed this" attribution comes from these free-form headers rather than the authenticated principal, so it can be spoofed by anyone with a valid token.

| POST | `/{id}/rooms` | Add a room | Body: `MeasurementRoom` + headers `X-User-Name`, `X-User-Role` | `MeasurementRoom` |

## 19. Cross-cutting issues worth a reviewer's attention

1. **Inconsistent response envelope.** Only `CustomerController`/`DashboardController` use `ApiResponse<T>`; everything else returns raw entities/`Page`/`List`/`Map`, and `AuthController` uses yet another ad hoc shape. A frontend or API consumer cannot assume `{success,data,message}` globally.
2. **Widespread `null`-user / mocked-auth pattern.** `LeadController`, `QuotationController`, `ProjectController` (several endpoints), `SiteVisitController` (several endpoints), and `TaskController.addComment` all accept `@AuthenticationPrincipal` (or nothing at all) and then hardcode `null` for the "performed by / created by / assigned by" argument passed into the service layer, instead of resolving the real user. Only `CustomerController`'s document/activity/note endpoints correctly use `Authentication.getName()`.
3. **`LeadController.getDashboardMetrics()`** (`GET /api/leads/dashboard`) returns fully hardcoded numbers and does not query the database at all.
4. **`NotificationController`** hardcodes `CURRENT_USER_ID = 1L` for every operation instead of deriving it from the authenticated principal.
5. **`AuthController.forgotPassword`** only logs the reset link to stdout ("MOCK EMAIL SENDER") — no real email is sent.
6. **`MeasurementController`** derives the acting user from client-supplied `X-User-Name`/`X-User-Role` headers rather than the JWT principal — spoofable by any authenticated caller and inconsistent with the rest of the API's auth model.
7. **Authorization coverage gap.** `@PreAuthorize`/role checks exist only on `CustomerController`. All other 16 controllers — including HR/payroll, purchasing, billing, project deletion, lead/quotation mutation — are reachable by any authenticated user regardless of role.
8. **`ExpenseController`** has no pagination on `GET /api/expenses` (returns the entire table), unlike every comparable list endpoint elsewhere in the API.
9. `TaskDTO`/`TaskMapper` exist unused; `TaskController` binds to the `Task` JPA entity directly instead.
10. `ReportController`'s date query params are parsed with `LocalDate.parse` and no error handling — a malformed `startDate`/`endDate` will bubble up as an uncaught `DateTimeParseException`, resulting in a generic 500 rather than a clean 400.
11. `DashboardSummaryDTO.RecentCustomer.company` is actually populated from the customer's `city` field, not a company name — likely a mislabeling bug.

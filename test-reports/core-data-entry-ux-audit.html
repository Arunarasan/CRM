Core Data-Entry UX Audit

How the Customer, Lead, and Quotation screens measure against the premium human-centered design standard — grounded in the actual code, ranked by impact, with a phased fix plan. No code changed yet.

Scope: Customers · Leads · Quotations Reviewed: 2026-08-20 Files read: 6 screens + 4 primitives Findings: 14 (5 critical, 9 secondary)
C+Overall

Solid foundation, uneven execution — and one screen holds the others back

The Leads module is genuinely good: sectioned forms, skeletons, inline errors, a reusable field kit. But Customers is a different app built to different rules — a flat 24-field wall with no feedback and no edit path — and the shell underneath all three has no mobile or tablet layout at all. The standard is mostly reachable by levelling the weak screens up to the Lead pattern, not by inventing anything new.

Critical findings

Fix these first — they break the standard outright

C1
The shell has no mobile or tablet layout — the desktop UI just squeezes
The sidebar is a hard-coded w-64 <aside> that is always rendered, with no collapse, hamburger, drawer, or bottom navigation. On a phone it eats ~40% of the screen and the content column collapses to an unusable strip. There is no md:hidden / responsive branch anywhere in the layout.
Violates §23 Responsive navigation · §11 Mobile as a distinct model · §5 “don’t solve responsiveness by shrinking.” This is the single highest-leverage fix: every screen inherits it.
DashboardLayout.tsx:55–88
Impact: every page on every phone and small tablet.
C2
Customer form is a flat 24-field wall — no sections, no progressive disclosure
Every field renders at once in one grid-cols-2 block inside a dialog: Individual and Business fields, GST/PAN, billing + site address, and raw Latitude / Longitude number inputs — shown to everyone regardless of customer type. Compare the Lead form, which is cleanly sectioned via shared primitives.
Violates §13 Long-form problem · §14 Progressive disclosure · §4 Human-first language (lat/long are database fields, not human ones).
Customers.tsx:126–244
Impact: highest-frequency create action in the CRM; primary onboarding surface.
C3
Customer create fails silently — no success, no error, no loading state
On submit, failure is swallowed by console.error and the dialog just… stays open. On success there is no toast and the Save button never shows a pending state, so a user on a slow connection can double-submit. There is no toast system anywhere in these screens. Leads does this better (inline error + “Saving…”), but even it has no success confirmation.
Violates §32 Human error handling · §34 Loading states · §35 Success feedback. “Never leave users wondering if the application is working.”
Customers.tsx:101–108 LeadFormDialog.tsx:83–87
Impact: data-loss anxiety + duplicate records on every create.
C4
Two different form-building conventions in the same app
Leads build forms from a shared kit — Field, TextField, SelectField, SectionTitle (leads/fields.tsx). Customers hand-rolls every <label> and raw <select> inline. Even input heights disagree: the base Input is h-9, the hand-coded selects are h-10. A user who learns one screen does not transfer that knowledge to the next, and neither do developers.
Violates §47 Design system · §48 Consistency rule. The fix (C2) and this fix are the same work: rebuild Customers on the Lead field kit.
leads/fields.tsx:1–116 Customers.tsx:128–243 ui/input.tsx:11
C5
Tables don’t transform for small screens — and Customers has no scroll guard at all
The Lead list is a 13-column table forced into horizontal scroll on mobile (§21 says use that “only when a real comparison is necessary” — a lead card isn’t). Quotations does the same with 8 columns. The Customers table has no overflow-x wrapper, so on a narrow viewport it either overflows the page or crushes columns. None of the three degrade to the card/list pattern the standard calls for.
Violates §21 Table design · §24 Responsive component transformation (“Table → Cards/List on mobile”).
Leads.tsx:294–371 Customers.tsx:272–325 QuotationList.tsx:112–167
Secondary findings

Real gaps, lower blast radius

S1
Filter panels steal content width instead of adapting per device
Both Customers and Leads render filters as a fixed right column (w-80 / w-72) that shrinks the table when open. The standard wants: sidebar on desktop → drawer on tablet → bottom sheet on mobile. Today it’s one behaviour everywhere.
Violates §24 Component transformation · §20 Mobile bottom sheets.
Customers.tsx:337–366 Leads.tsx:388–446
S2
No edit path for a customer — the dialog is create-only
The “Add Customer” dialog can’t edit. Changing one phone number has no inline-edit affordance anywhere in the list, unlike the standard’s pattern of small, context-preserving edits. Leads, by contrast, reuse one LeadFormDialog for both create and edit.
Violates §18 Inline editing · §38 Preserve context.
Customers.tsx:118–250 LeadFormDialog.tsx:16–36
S3
The system asks for data it already has
A lead already carries name, phone, company, GST, and full address — but converting or creating a customer doesn’t pre-fill from it, and the Lead form doesn’t autocomplete against existing customers. Users re-type known data. The address is entered twice within a single lead (billing + site) with no “same as” shortcut.
Violates §15 Smart form design · §40 Smart data entry (“don’t ask for information the system already knows”).
Customers.tsx:31–35 LeadFormDialog.tsx:127–148
S4
Wrong mobile keyboards — phone and pincode are plain text inputs
Phone, alternate phone, WhatsApp, and pincode use default text inputs, so mobile users get the alphabetic keyboard for numeric data. No type="tel" / inputMode="numeric". Email is correct in most places.
Violates §39 Responsive keyboard experience.
Customers.tsx:175,179,229 LeadFormDialog.tsx:131–133,144
S5
Even the good Lead form is one long scroll with no disclosure
It’s sectioned (good) but still shows every section at once — Scope of Work checkboxes, budget, timeline, three assignee pickers, image capture — regardless of lead type. Optional/advanced groups (assignment, images, detailed requirements) are prime candidates for collapse-until-needed or a light 2–3 step flow.
Violates §14 Progressive disclosure · §17 Multi-step forms (used only where it genuinely helps).
LeadFormDialog.tsx:117–199
S6
Empty and loading states are inconsistent across the three
Quotations has the best pattern (a proper EmptyState with guidance). Leads shows an icon + text but no call-to-action. Customers shows bare “No customers found” text — and has no skeleton at all, so the table is just blank until data lands, while Leads and Quotations both skeleton correctly.
Violates §33 Empty states (explain what’s missing + what to do) · §34 Loading states.
Customers.tsx:316–322 Leads.tsx:323–329 QuotationList.tsx:136–142
S7
Two search boxes, one of them fake
The global header has a “Search…” input that is wired to nothing, while each page has its own real search below it. A decorative search box that does nothing is a direct trust and clarity cost — users try it and get silence.
Violates §2 The 5-second rule · §6 Predictable navigation. Either make it a real global search or remove it.
DashboardLayout.tsx:94–97
S8
System jargon leaks into user-facing labels
Quotations surfaces raw enum values (Mode: FULL_HOUSE), and terms like BOQ / GRN appear unglossed. The quotationMode cell prints the code, not a human phrase. Most action labels elsewhere are excellent (“Save Customer”, “Create Lead”) — this is a narrow leak, not a pattern.
Violates §4 Human-first language. Map enums → readable labels the way status already is (QUOTATION_STATUS_LABELS exists — extend the pattern to mode).
QuotationList.tsx:149
S9
Fragile magic-number heights won’t survive the responsive work
The Kanban board and filter panel use hand-tuned viewport math (h-[calc(100vh-390px)], max-h-[calc(100vh-380px)]). These assume a fixed header/toolbar stack and will break the moment the shell becomes responsive (C1). Worth replacing with flexbox constraints as part of that pass.
Violates §52 Practicality — “A beautiful UI that feels slow / breaks is not premium.”
Leads.tsx:221,389
What’s already right

Don’t lose these in the rework

  • Action labels are human. “Save Customer”, “Create Lead”, “Add Lead”, “Generate from a BOQ” — verbs that say what happens. Keep this voice.
  • The Lead field kit is the design-system seed. leads/fields.tsx is exactly the shared component layer §47 asks for — it just needs to be adopted app-wide and grown (drawer, bottom sheet, toast).
  • Lead form UX fundamentals are in place. Sectioned layout, inline error surfacing, disabled+“Saving…” button, image capture, and one dialog reused for create and edit.
  • Skeletons + debounced search + optimistic Kanban drag on Leads and Quotations show the team already knows the right patterns — they’re just not applied evenly.
  • Quotations’ EmptyState is the empty-state pattern to standardize on.
Roadmap

A sequenced plan — each phase is usable on its own

Ordered by leverage. Phase 1 is a hard prerequisite for the responsive work in every later phase, which is why it comes first even though it isn’t a data-entry screen.

1

Responsive shell + a shared feedback layerFoundation

Unblocks all mobile/tablet work · closes C1, C3, S7

  • Give DashboardLayout three modes: sidebar (desktop) → collapsible rail (tablet) → drawer + bottom nav (mobile).
  • Add one app-wide toast system; wire success + human-readable error into every create/update (starting with the silent Customer create).
  • Decide the global header search: make it real or remove it. Remove the duplicate logout.
2

Rebuild the Customer form on the Lead field kitHigh impact

Closes C2, C4, S2 · the biggest single-screen win

  • Replace the 24-field wall with sectioned Field/TextField/SelectField groups: Basic → Contact → Address → Business.
  • Progressive disclosure: reveal Company/GST/PAN only when type ≠ Individual; hide lat/long behind a “Pin on map” affordance.
  • Make the dialog do create and edit, mirroring LeadFormDialog. Add pending state + toast.
3

Lists → responsive cards, filters → drawer/sheetBroad

Closes C5, S1, S6 across all three screens

  • Build one ResponsiveList: full table on desktop, card/list on mobile — apply to Customers, Leads, Quotations.
  • Filters become a right sidebar (desktop) / drawer (tablet) / bottom sheet (mobile) via one shared component.
  • Standardize empty + skeleton states on the Quotations EmptyState pattern; add the missing Customer skeleton.
4

Smart entry & polishRefinement

Closes S3, S4, S5, S8, S9

  • Pre-fill customer from lead on convert; autocomplete existing customers in the lead form; “same as billing” address shortcut.
  • Correct input types/inputMode for phone & pincode; add light progressive disclosure to the Lead form.
  • Map remaining enums (quotation mode) to human labels; replace magic-number heights with flex constraints.
The one-line takeaway The standard is closer than the grade suggests. You already built the right patterns once — in Leads. The work is mostly propagation and a responsive shell, not invention: make the shell adapt, level Customers up to the Lead pattern, and factor the shared pieces (list, filter, toast, field kit) so consistency comes for free.
